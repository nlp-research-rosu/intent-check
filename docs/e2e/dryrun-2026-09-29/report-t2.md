# Intent Check dry run — tester t2 (Claude Code + subagents)

## Summary

Core "edit -> upload -> report" loop works even when the edit is made by a subagent — foreground and background subagent writes both get diffed and uploaded on the parent's next Stop hook. But subagent-awareness is genuinely absent as the code review suspected: no `agent_id` anywhere, worktree-isolated edits get buried under a `.claude/worktrees/...` mirror path inside `.intent/` (not at the file's real path), a background subagent's edit can be silently deferred to the *next*, unrelated turn, and the assistant once cited a stale/wrong report URL as if it applied to the worktree change. No concern wakes fired in any scenario, so I could not observe wake behavior — only silent no-concern uploads.

## Bugs

1. **Major — worktree-isolated subagent edits filed under a buried `.claude/worktrees/...` mirror path in `.intent/`, not the real file path.** Repro: ask Claude Code to run a subagent with `isolation: worktree` that edits an existing tracked file. The edit lands only in `.claude/worktrees/agent-<id>/<file>`, never in the main tree. The plugin still uploads it, but writes the report to `.intent/.claude/worktrees/agent-<id>/<file>/` instead of `.intent/<file>/`. Evidence:
   ```
   $ find .intent -path "*worktrees*"
   .intent/.claude/worktrees
   .intent/.claude/worktrees/agent-a858f77a62069eb12
   .intent/.claude/worktrees/agent-a858f77a62069eb12/src
   .intent/.claude/worktrees/agent-a858f77a62069eb12/src/logger.js/{INTENT.md,VERDICT.md,meta.json,...}
   $ find .intent/src -maxdepth 0 -iname logger.js   # nothing — no entry at the expected path
   ```
   A user checking `.intent/src/logger.js/` (the natural place to look) will never find this review, and if the worktree branch is later merged manually with no further "real" edit registered on the main tree, that merge never gets checked at all.

2. **Major — stale/mismatched report URL cited in the assistant's own reply.** In the worktree turn, the assistant's response said `Intent Check reported no concerns: https://web-staging-7e1c.up.railway.app/r/QSrT6D3roohEHUkCFTosU9` — but that job (`QSrT...`) was a review of `src/health.js` from a *previous* turn, already `job.done` at 20:12:03. The actual review of the worktree `logger.js` edit (`PMpE96A74On5GOj9fwJAMc`) was submitted at 20:12:19 and didn't finish until 20:12:36 — after the assistant had already spoken. The assistant effectively cited a plausible-looking but wrong report because the hook fed it the last-known job info rather than waiting for/attaching the actually-relevant one. This is dangerous UX: a user skimming the chat would believe the worktree change was vetted when it wasn't (yet).

3. **Minor — background subagent edits can be silently deferred to an unrelated later turn.** When a background subagent is still writing at the moment the parent's own turn ends, that turn's Stop hook reports `nothing_to_check` (0 files) and no upload happens for that turn. The edit is only caught by the *next* Stop hook, whatever prompt triggers it — in my test, a "commit this with git" prompt for a different purpose ended up being the one whose Stop swept up and uploaded the health.js change. No data was lost and no duplicate/garbage upload occurred, but the intent snapshot review is effectively decoupled from the turn/prompt that actually produced the edit, which could mis-attribute intent if the two turns had different unrelated user asks.

4. **Confirmed — no `agent_id` anywhere.** `grep -c agent_id ~/.claude/plugins/data/intent-t2-inline/intent.log` → `0` across all five scenarios, including the 3-parallel-subagent and worktree cases. The debug log correlates everything purely by `session` + `turn`, with subagent tool calls (`PostToolUse` for `Write`/`Edit`) simply appearing under whichever `turn` id happens to be active in the parent session at the moment the hook fires — sometimes the launching turn, sometimes a spillover into the next turn. This matches the code-review concern exactly.

5. **Minor — `/intent:off` mentioned instead of `/intent-t2:off`.** When I asked "are we connected," the assistant told me I could turn it off with `/intent:off`, the unrenamed command name, even though this plugin copy is namespaced `intent-t2`. Cosmetic but could confuse a user running multiple renamed copies.

## UX notes

- Connect flow is smooth: clear "connect your account" message with link, `user_code` easy to find in `connect.json`, "connected" confirmation on the very next prompt.
- All five scenarios silently returned `no_concerns` — I never got to observe an actual wake/interruption during this dry run, so I can't speak to how the "Intent Check:" wake message reads or whether the agent reliably fixes flagged code. Worth another pass with a change deliberately designed to trigger a concern the LLM can't miss (e.g., an off-by-one on the actual limiter value, not just an ambiguous identity assumption).
- Latency was consistently reasonable: 17–43 seconds per check across all jobs, well within the stated 40–80s budget.
- The rate-limiter INTENT.md correctly surfaced real ambiguities (identify-by-header spoofability, rolling vs. calendar-minute window) as "assumptions made explicit" — genuinely useful, well-written summaries — but it stopped short of promoting any of them to an actual "concern," even the spoofable-identity one, which does undercut the literal request ("per user"). This feels like a judgment-calibration issue: the reviewer is good at articulating ambiguity but conservative about calling anything out.
- Claude Code auto-backgrounds Task/Agent calls almost regardless of phrasing ("foreground", "wait for it") — this is a host behavior, not a plugin bug, but it means "foreground subagent" scenarios are hard to force in this CLI version; every subagent in this run ended up going through the same background code path.
- The debug log is clean, well-structured JSONL and easy to correlate by timestamp — good for this kind of investigation.
