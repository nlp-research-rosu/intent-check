## Bugs

1. **Minor/new — worktree-isolated subagent concern doesn't trigger the spontaneous wake.** Repro: have Claude Code run `Agent(isolation:"worktree")` to edit a tracked file with a real concern. The job uploads and completes correctly (fixed, see check #3), but the idle session sits there with no wake for 5+ minutes; the concern only reaches the agent on the user's next prompt (via `additionalContext`, same channel as the "no concerns, named file" note). This is a regression relative to the normal single-turn flow (check #1b), where the wake fired within ~90s of `job.done` using the exact same mechanism (`stop.wake` in `intent.log`). Worth checking whether the wake logic's "is the session idle" check is confused by the transient "waiting for background agent" UI state that a worktree/background subagent leaves behind.

2. **Minor — the new "clean change, name the file" note isn't always rendered as a distinct system line, and can lose the URL.** In check #2, the hook correctly delivered `additionalContext` containing (per the plugin's own test suite in `src/test/render.test.js`) the format `Intent Check: no concerns in <file> · <url>`. But Claude Code displayed the "connected"/"found concerns" messages as their own `⎿ ... says:` block verbatim, while this one got woven into the assistant's own prose and the URL was dropped entirely. A user relying on the URL to spot-check the report would miss it. Not clearly a plugin bug (may be a Claude Code rendering/host-side inconsistency for `additionalContext` vs. hook `systemMessage`), but worth a look since the file-name UX gain is only half-realized if the link disappears.

3. **Unchanged from t4 — prover-unreachable is still completely silent.** `INTENT_API_URL=http://127.0.0.1:9` → `job.submit_failed status:0 code:network`, turn not slowed (good), but no user-visible signal at all, same turn or later. Not the fix under test here, just confirming it's still open.

## UX notes
- **The worktree path fix is solid and the headline win of this recheck.** `find ~/shop/.intent -maxdepth 4` never showed a `.claude` subdirectory in any of the three scenarios run against worktree-isolated edits; `.sent.log` and `meta.json` consistently pointed at the real file path (`pricing.js`), not `.claude/worktrees/agent-.../pricing.js`.
- **Bad-key recovery is now a real fix, not just status quo.** Compared to t4's report (completely silent 401, stale `.intent/` left behind with no hint anything was wrong), this run's 401 cleared the stored key and surfaced a working connect link on the very next prompt, in the middle of an otherwise-normal answer. This closes the most severe bug from the prior round.
- **LLM verdict quality remains good and non-trivial.** Both concerns raised (NaN `price_cents` bypassing the non-negative guard in #1b; NaN-producing non-numeric `price` in #3's `computeTotal` validation) were genuine, specific, and each pointed at the exact line. The agent's fixes were correct and it didn't over-claim ("Intent Check's concern was valid, and I've fixed it").
- **No double wakes anywhere.** Across all six scenarios, every recheck after a fix came back cleanly with no repeat interruption.
- **Permission prompts for `Bash`/`node`/`python3` despite `--permission-mode acceptEdits`** slowed down testing (each turn needed a manual `Enter`) — expected given the harness's permission model for shell commands, not a plugin issue, but worth remembering for future dry runs.
- **Placeholder ghost text** ("Try 'commit this'", "Try 'how do I log an error?'") sometimes lingered in `tmux capture-pane` snapshots of the empty input box and looked like unsent typed text at first glance — harmless UI polish text, not a real input-buffer bug.
